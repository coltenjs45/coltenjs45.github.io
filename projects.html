Senior design: AI Arcade

Iowa State senior design team sdmay27-06, 2026–2027, for client Josh Clausman of Silvertree Studios

Description
A retro arcade that ships a small library of classic-style games, like Pong, Breakout, and Frogger, along with an AI agent that can modify those games or write entirely new ones. The games are written in Rust on the macroquad framework and run in the browser through WebAssembly, and are being brought to a physical arcade cabinet built around a Raspberry Pi 5. A separate authoring tool lets a person describe a change, has the AI agent make it, and shows a live preview before anything is accepted.
My role
I have two jobs on the team. On the hardware side, I'm building the physical arcade: setting up the Raspberry Pi 5 and fitting it into the cabinet with its screen and controls. On the AI side, I develop the skills in the harness that the AI agent works from when it edits games live. These are written instructions that keep the agent efficient and make it harder to attack through prompt injection, where text hidden in a request or a file tries to hijack the agent into doing something it shouldn't.
Skills gained
Setting up and configuring a Raspberry Pi 5 on Linux and integrating it with arcade hardware. Writing instructions that steer an AI agent toward fast, correct changes. Thinking like an attacker about AI systems: how prompt injection works, where untrusted input enters, and how to limit what a hijacked agent could do. Working with an outside client and a team split across hardware, software, and AI.
Big picture
AI Arcade turns players into co-authors: someone with no programming background can describe the game they want and play it minutes later. It is also a small, concrete test of a bigger question in security: how to let an AI write and ship code safely. The arcade that players use and the AI that writes code run on separate systems, every game is held to a fixed input contract, and AI-written changes are previewed and reviewed before they reach the arcade.

Multiplayer card games app

COM S 3090 App Development team project, 2023, built with Java, Android, Spring Boot, and MySQL

Description
An Android app, built from scratch, where players join a shared server and play several different card games against each other. The project was split between a frontend team building the Android client and a backend team building the game server.
My role
Developer on the backend team, which built the Spring Boot game server and MySQL database that the Android app talks to. Midway through the semester the two halves of the project felt disconnected, so another teammate and I set up a recurring weekly meeting to review what was due that week and share progress across both teams. That gave everyone clear, manageable weekly goals, and the project went on to win best project of the semester.
Skills gained
Git branching and merging on a shared repository; socket connections for real-time play between client and server; the Spring Boot framework with a MySQL database and Maven builds; and coordinating two sub-teams toward one product.
Resources used
None of Git, sockets, or Spring Boot were taught directly in class, so we learned them from official documentation, example code we found online, and teaching each other. We used Maven to build the server and MySQL to store game and player data.

Mine Sweeper: CyBot field robot

CprE 2880 embedded systems final project, built in C on a TI TM4C123 microcontroller with a Python control GUI

Description
Clearing a minefield by hand is dangerous, especially in dense terrain. Our team of four built Mine Sweeper, a robot that sweeps a test field imitating a sectioned-off minefield in a forest. A driver steers the CyBot (an iRobot Create base with a TM4C123 microcontroller) from a Python GUI over a Wi-Fi socket. The robot scans with infrared and ultrasonic sensors on a servo, detects holes and field boundaries with its cliff sensors, reports bumps, and tracks its own position so the GUI can draw a live map of the field and every object it finds.
My role
I led the team's development and wrote most of the robot's embedded C code, everything outside the Python GUI. My main job was getting the CyBot to read its surroundings with every sensor on board: I set up the servo-mounted infrared and ultrasonic (ping) scanning, calibrated the IR sensor against measured distances so its readings converted to real distances, and wired up the bump and cliff sensors so the robot reported collisions, holes, and field boundaries to the driver as they happened.
Skills gained
Embedded C on a real microcontroller: timers, interrupts, UART, ADC, and PWM servo control. Calibrating a noisy IR sensor against measured distances. Socket communication between the robot and a pygame GUI. Dead-reckoning position tracking with vectors. Splitting one system between four people and integrating it for a live demo.
Resources used
TI TM4C123 datasheet and TivaWare driver library, the course's CyBot and Open Interface libraries, Code Composer Studio, Python with pygame, and our own IR calibration data.

Pipelined RISC-V processor

CprE 3810 computer organization semester project, written in structural VHDL

Description
Over the semester, my partner and I built three processors that run the same RISC-V instruction set: a single-cycle design, a five-stage pipeline where hazards are avoided in software by inserting NOPs, and a five-stage pipeline that detects and resolves hazards in hardware with forwarding and stalls. We benchmarked all three on four test programs, including a recursive merge sort, and compared their cycle counts and maximum clock speeds after synthesis. The hardware-scheduled pipeline was the fastest of the three on merge sort.
My role
Two-person team with Graeme Anderson. I led design and testing for the software-scheduled datapath and its synthesis, the pipeline register updates, control hazard avoidance, and testing of the hardware-scheduled pipeline.
Skills gained
Structural VHDL; datapath and control design; pipeline registers with stall and flush; data hazard forwarding and load-use stalls; resolving branches early in the decode stage so no stages need flushing; writing RISC-V assembly test programs; reading waveforms in QuestaSim; and finding the critical path from synthesis results.
Resources used
The course textbook and RISC-V specification, the CprE 3810 toolflow and test suite, QuestaSim for simulation, synthesis reports for timing, draw.io for schematics, and Git for version control.
